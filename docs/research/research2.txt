The most important result so far

I think the README underplays this:

You have already demonstrated the central MoE proposition at microscope scale.

The top-1 model has roughly:

1.86× total parameters

That does not prove MoE is better at this scale.

You can add dormant/specialized model capacity without proportionally increasing the computation performed for each token.

The second important result: specialization is actually happening

This is probably the most interesting scientific result currently in the repo.

For four experts, no specialization corresponds to approximately:

$$ 1/4 = 0.25 $$

The top-1 system reports:

$$ \text{specialization}=0.61 $$

and the router was not directly given the task-family tag.

That suggests the hidden representations contain enough task information for routing to segregate work.

That is exactly the phenomenon you need before ideas like:

expert caching,
heterogeneous CPU/NPU execution,
expert placement,
expert quantization,
expert swapping,

become interesting.

If requests were distributed uniformly across experts, many of those later techniques would be much less useful.

So I would elevate this result prominently.

templated prose

Therefore the experiment shows:

Experts can specialize when the underlying task distribution has obvious latent structure.

That's not a flaw. It is exactly the right microscope experiment.

The data-scaling experiment may be the strongest science in the README

The README currently treats DS01 almost as a side experiment. I think it deserves much greater prominence.

At 120 examples:

Dense val loss: 3.48
MoE: 3.49

At 480:

Dense: 1.66
MoE: 1.42

At 960:

Dense: 1.11
MoE: 1.22

Meanwhile doubling epochs from 200 → 400 at only 120 examples makes both models worse.

That tells you several things.

First, the poor early generalization was primarily data-limited, not evidence that the architectures were broken.

Second, extra optimization cannot substitute for information.

Third, the small MoE does not consistently dominate dense. It wins at 480 and loses at 960.

That is exactly the kind of result that gives the project credibility.

A less careful demo would only report the favorable 480-example point.

Sparse dispatch is an excellent experiment

This is perhaps the cleanest demonstration of an optimization technique.

Dense-masked MoE:

run every expert, then zero unwanted outputs.

Sparse MoE:

gather only tokens assigned to each expert, execute that expert, then scatter the results back.

The experiment shows:

Exact mathematical equivalence

$$ \max |\text{dense}-\text{sparse}| = 0 $$

while expert row evaluations fall:

$$ 13,440 \rightarrow 3,360 $$

which is exactly 4× less expert work.

And then comes the especially valuable result:

Sparse execution is currently slower.

0.74 ms/window versus 0.42 ms/window.

That is not a failure.

It demonstrates a crucial systems principle:

Reduced FLOPs do not automatically mean reduced latency.

At microscope scale, dispatch overhead dominates the tiny matrix operations being avoided.

This is precisely the sort of issue that FreeToken-style systems must contend with at full scale.

I would make this one of the project's headline findings.

5. SSD/HDD swapping has a counterintuitive answer at microscope scale

For an 8.4-KiB FP64 expert, theoretical bulk transfer time is minuscule.

Approximate transfer-only costs:

Device assumption	8.4-KiB FP64 expert	1.05-KiB INT8	536-B INT4
HDD @ 150 MB/s sequential	0.057 ms	0.007 ms	0.004 ms
SATA SSD @ 500 MB/s	0.017 ms	0.002 ms	0.001 ms
NVMe @ 3 GB/s	0.0029 ms	0.00036 ms	0.00018 ms

But those figures are almost misleading.

The real picture is:

INT4 expert on disk
        |
        | 536 bytes
        v

HDD:
[ seek + rotation ................. ][copy]
  several milliseconds               ~0

SSD:
[command/I/O latency][copy]

RAM:
[memcpy]

For these microscopic experts, I/O latency overwhelms bandwidth.

An HDD random expert miss could easily cost orders of magnitude more than the inference itself. The current DN01 inference metric is ~0.020 ms/token, whereas an HDD random lookup is conventionally millisecond-scale.

That gives XC01 a very nice pedagogical objective:

At tiny scale, caching is not about reducing bytes. It is about avoiding storage access latency.

And it explains why cache hit rate matters.

TTFT =
    model initialization
  + prompt processing
  + routing
  + expert miss latency
  + expert execution
  + LM head

    routing
  + cache hit
  + expert execution
  + LM head

That is exactly the systems behavior this project eventually wants to teach.

## What have we learned so far?

### More stored capacity without proportionally more active compute

Dense:
3,812 total / 2,996 active parameters per token

Top-1 MoE:
7,096 total / 3,064 active parameters per token

### Experts actually specialize

Top-1 specialization:
0.61 vs 0.25 uniform baseline.

### Sparse compute does not automatically mean faster execution

Sparse dispatch reduces expert work 4× while producing identical output,
but is currently slower because dispatch overhead dominates these tiny experts.

### Data matters more than extra epochs

Increasing training data improves held-out behavior substantially.
Simply doubling training epochs on the small dataset worsens validation loss.

[Current findings →](docs/results/current-findings.md)

The navigation principle

I'd use three levels at most for ordinary reading:

README
   ↓
topic index
   ↓
focused document

Anything deeper than that should generally be reference material, not required reading.

So the overall experience becomes:

README tells me the story.

Topic indexes tell me where to look.

Focused pages teach one thing.

Reference pages preserve all the evidence.

That structure also maps naturally onto a future Wiki without maintaining a completely different conceptual organization.
